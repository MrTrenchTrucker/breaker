# AGENTS.md — android/modules/sync/

## Purpose

Offline-first sync queue, idempotent push (F13, N12). Offline-first sync queue (F13). Every transcription syncs to the server when reachable - even local-only mode - with no data loss on offline dictation.

**Build phase:** Phase 11, development only. Every push is built at `key_version` 0: the body is the R1 JSON object, base64 encoded, with no cryptography. The `key_version` 1 form, the `key_version` replace, the re-key and the pending-sealed fetch are not built. Needs first: `core` (on main) and the server's `sync-api`.

## Owns

The offline-first sync queue on the phone, and the idempotent push (F13, N12) of its rows at `key_version` 0.

## Public Interface

- `QueuedSyncService` implements `core.SyncService` (`enqueue`, `pushPending`). Build it with `QueuedSyncService.create(context, uploader, probe, pullTransport, pullSink)`; the two pull arguments are optional and default to null. `pendingCount()`, `parkedCount()`, `parkedReason(clientId)` and `close()` are public too. `pendingCount()` leaves parked rows out. When both pull halves are given, `pullTrigger` is non-null and `pushPending` runs one pull cycle after a finished drain, under the same drain mutex; `enqueue` never runs a pull.
- `recordKeys: RecordKeys? = null` is the second to last parameter of the `QueuedSyncService` constructor and of `create(...)` (after `pullSink`, before `pendingTransport`). `RecordKeys` is the core port that hides the key, the nonce and the associated data; this module never imports crypto. With no port (the default) every push and pull is as before. With a port, `pushPending` seals each row's R1 body bytes (`SyncBodyCodec.encodeBody`) through `seal` and sends `SyncPush(clientId, sealed.keyVersion, sealed.encrypted, null)`; the key version is read from `currentKeyVersion()` at push time. A port that holds no keys (version below 1) or cannot seal stops the drain with one failure, the rows stay queued and nothing is pushed in plain form (`stopBecausePortHasNoKeys`, in `RecordKeyPush.kt`, the one place a later ruling would change). A 409 on a port push is remembered per service instance by key version (`RefusedKeyVersion`): each later drain stops at once (`stopBecauseKeyVersionRefused`, one failure, no seal, no upload) until the port reports another version; a 409 never parks, removes or drops a row. On the pull, `PullApplier` and `PulledRowBody.read(record, keys)` open a key_version 1 or higher row through the port and read the bytes with the lenient `SyncBodyCodec.decodeBody`; a null from the port is counted unreadable.
- Own-record migration (internal, `RecordMigration.kt`): with a port and a pull transport, `QueuedSyncService` builds a `RecordMigration` that shares the 409 memory (`RefusedKeyVersion`) with the drain, and `pushPending` calls `migration?.pass()` right after the pull, under the drain lock. A pass reads `currentKeyVersion()` (below 1 does nothing; a changed version starts a new walk), lists ALL own records with `PullLoop.run(transport, null)` and never reads or writes the stored pull cursor, then walks the records in ascending `change` order from its own cursor. A deleted record, one at a key version at or above the current one, and one whose id is queued (a local edit wins) are passed over. Every other record is re-sealed through the port member `reseal(clientId, keyVersion, encrypted)` (the plaintext never reaches sync) and pushed at the same client id and the new key version through the uploader; the server swaps it atomically. At most 50 records are tried per pass. A null from the port counts `unconvertible` and the pass goes on; `FAILED`, an exception and a status other than 400, 409, 413 and 429 count `failed` and stop; `UNREACHABLE` stops; a 429 stops and keeps its Retry-After seconds; a 409 stops and is remembered by key version; a 400 or 413 counts `failed` and the pass goes on. A stopped pass retries the record it stopped at on the next drain. A complete walk clears `pending` until the key version changes, even when it met unconvertible records or permanent refusals (400, 413), which are only counted; only a transient problem (`FAILED`, an exception, another status) keeps it. `QueuedSyncService.migrationCounts()` (internal) reads `MigrationCounts` (`replaced`, `unconvertible`, `failed`, `retryAfterSeconds`): numbers only, never an id or a text, nothing is logged.
- Push row (internal, `PushRow.kt`): `QueuedSyncService` builds one `PushRow` over its database, uploader, port and the shared 409 memory (`RefusedKeyVersion`), and the drain calls `pushRow.send(entry)` for every push row. It builds the push (`buildPush` with no port, `buildPortPush` with one), sends it through the uploader and answers a `PushRowResult`: `Done` (the uploader's outcome and, for a 429, its Retry-After seconds), `Parked` (a 400 or 413 parked the row), `Skipped`, `NoKeys` or `KeyVersionRefused`. A 409 with a port is remembered by key version; an exception from the port propagates and one from the uploader is `FAILED`. The drain keeps the counts, the stop reports, the removal of a confirmed row and the delete rows, which never reach `PushRow`.
- Pending-sealed conversion (internal `PendingConversion.kt`, `PendingSealedDecoder.kt`, `PendingJson.kt`; public seam `PendingSealedTransport.kt`): `pendingTransport: PendingSealedTransport? = null` is the last parameter of the `QueuedSyncService` constructor and of `create(...)` (after `recordKeys`). `PendingSealedTransport` is a public `fun interface` with `fetch(): PullTransportResult`; the app sends GET /v1/sync/pending-sealed with the user's token and answers `Answered(status, body)` or `Unreachable`, never throwing for those, and reads at most 8 MiB of response text (`PendingSealedDecoder.MAX_BODY_CHARS`); the server has no pagination and no limit on the list. With a port and this transport, `pushPending` calls `pendingConversion?.pass()` right after `migration?.pass()`, under the drain lock, guarded like the migration. A pass reads `currentKeyVersion()` (below 1 does nothing; a 409 remembered by the drain, in the shared `RefusedKeyVersion`, does nothing), fetches the list and ends quietly on `Unreachable`, a status other than 200 or a transport that throws. `PendingSealedDecoder.decode` returns a `PendingList` (`rows`, `skipped`) and refuses the WHOLE list only for a structural fault (one failure counted, no port call, the rows stay on the server): a body over 8 MiB (checked before parsing), a top value that is not an array, text that is not JSON (bad token, bad escape, unterminated, trailing text, a control character in a string, white space other than space, tab, line feed, carriage return) and nesting deeper than 16 levels (the top array is level 1; the depth is checked before a container is entered, so a 100000 level body cannot overflow the stack). There is no row-count limit. A ROW that fails its own checks is SKIPPED, never a refusal: not an object, a member other than `id`, `sealed_box`, `created_at`, a duplicate, missing or non-string member, an `id` that is not a lowercase canonical UUID, a `sealed_box` that is not strict padded standard base64 (it must re-encode to the same text) or is over 2 MiB of text, an empty `created_at`. Every row is first read completely as JSON by `PendingJson.kt` (its own small strict reader, any value kind), so a junk row never hides the rows after it. An empty array and an empty `sealed_box` are valid (the port answers null for an empty box). A skipped row is a `SkippedRow` (`index`, `id` only when it is a canonical UUID, `fingerprint`: a 64-bit FNV-1a hash of the row's raw text, plain arithmetic, no digest class); nothing else of the row is kept. A decode-level skipped row is remembered ONLY by its fingerprint (`badFingerprints`), never by its id, so it can never hide a good row with the same id. A row whose id is queued is skipped (a local edit wins); at most 50 rows are tried per pass. Each row goes through the port member `convertSealed(clientId, sealedBox)` (the box key and the plaintext never reach sync; the box array is zeroed after the call) and is pushed as a NEW record, `SyncPush(id, sealed.keyVersion, sealed.encrypted, null)`, by the drain's uploader. A null from the port counts `unconvertible` once and the id goes into `badIds`: the row is not asked of the port again until the key version changes or the process restarts, so unconvertible rows at the head cannot starve the rows behind them; the row stays on the server. Outcomes as the migration: `CONFIRMED` counts `converted`; `UNREACHABLE` stops; `FAILED`, an exception and a status other than 400, 409, 413 and 429 count `failed` and stop and mark nothing; a 429 stops and keeps its Retry-After seconds; a 409 stops and is remembered by key version; a 400 or 413 (a permanent refusal) counts `failed`, puts the row id into `badIds` (the row is not sent again until the key version changes or the process restarts) and the pass goes on. `badIds` and `badFingerprints` are in memory, are cleared when the key version changes, and each holds at most `MAX_MARKED` (10000) entries: a bad row met when a set is full is still skipped and counted in that pass but not remembered, so it is counted again on every later pass (the cap stops memory growth). Two rows with one id are both tried (the server dedupes). `QueuedSyncService.pendingCounts()` (internal) reads `PendingCounts` (`converted`, `unconvertible`, `failed`, `skipped`, `retryAfterSeconds`): numbers only, never an id, a box or a text; `skipped` counts each distinct skipped row once. `QueuedSyncService.pendingSkips()` (internal) reads `PendingSkips` (`count`, `indices`): the list positions of ALL rows skipped in the last pass that decoded a list, including rows skipped silently because they were seen before; positions only, never content. The sync module has no logger and logs nothing; both readers are internal. `PlainPush.kt` holds the internal `buildPush(entry)` that `PushRow` calls on the no-port path.
- `SyncUploader`: `fun upload(push: SyncPush): UploadOutcome`. `UploadOutcome` has `CONFIRMED`, `UNREACHABLE` and `FAILED`, in that order. An uploader reports a refusal about the row itself by throwing `PermanentRefusalException(status, reason)`; only status 400 and 413 park the row (ADR-038).
- `PullTransport`: `fun fetch(request: PullRequest): PullTransportResult`, the seam the app implements for the pull (the app's `wiring/PullChainWiring.kt` builds `PullHttpTransport`). `PullTransportResult` is `Answered(status, body)` for any HTTP answer, the status and the body text exactly as received, or `Unreachable` when the server could not be reached; an implementation never throws for those. `PullRequest` is public only for its `path()` and `query()`; its factories stay internal, so the app cannot build one.
- `PullTrigger`: a public `fun interface` with `run()`, the never-throwing seam the app reads from `QueuedSyncService.pullTrigger`. `QueuedSyncService` builds the cycle over its own database (the cursor store and the queue probe) and the app's `PullTransport` and `PullSink`; `run()` swallows every exception, so a failing pull changes neither the stored cursor nor the drain's report, and the next drain retries.
- `OlderPullTransport`: `fun fetch(request: OlderPullRequest): PullTransportResult`, the seam the app implements for the older-rows read (`GET /v1/transcriptions/older`, a read that writes nothing); `OlderPullRequest` is public only for its `path()` and `query()` (`older_than=<ms>` or `older_than=<ms>-<change>`). The internal `OlderPageReader` reads one page: a 200 is decoded with the pull decoder and each row opened with the pull row reader, and 400, 401, 403, 429 and any other status map to the core `OlderResult` kinds. A delete record or a row that cannot be read is left out and counted; nothing is stored and no cursor moves, so the pull applier, loop, run and cycle are not used. The public adapter `OlderHistorySyncAdapter` implements the core `OlderHistory` port over it, and the app's transport is built by `wiring/OlderRowsWiring.kt`.
- The push and the body types come from api-contracts: `dev.breaker.shared.api.SyncPush` and `dev.breaker.shared.api.sync` (`SyncBody`, `SyncBodyCodec`, `SyncBodyException`, `SyncSource`). The module calls `SyncBodyCodec` and never writes the wire form by hand (ADR-017).

**Queue:**
- `enqueue` stores one row: the transcription id as `client_id`, the text, the source as its wire text (`local` or `server`), the model, the duration and `created_at` (epoch milliseconds, when the transcription was made). Audio is never queued.
- `pushPending` asks the `ConnectivityProbe` first. When the server is reachable it sends the rows that were queued when the drain started, oldest first, by `seq`, and returns a `SyncReport`. A row queued during the drain waits for the next drain. Only one drain runs at a time.
- Every push is `SyncBodyCodec.plainPush(clientId, body)` at `key_version` 0.

**Uploader:** the app supplies it. A class that implements `SyncUploader` also needs api-contracts on its own classpath (the app declares it when it wires). It sends the `SyncPush` to `POST /v1/sync` with the user's token and answers `CONFIRMED`, `UNREACHABLE` or `FAILED`, or throws `PermanentRefusalException` for a 400 or 413. This module has no HTTP client.

**Pull transport and loop:** `PullTransport` is the public seam the app implements (answered or unreachable, never throws for those; see Public Interface) and `PullLoop.run` (internal) drives page after page with six outcomes: `Ok`, `BadCursor`, `Gone` (a 410), `Other`, `Unreachable` and `Refused`. No-progress (next equals the cursor just sent, a page with more true holds no records, or, when both the cursor sent and next are incremental cursors of two digit parts, next names another account or its change number is not past the cursor's) and the page cap of 1000 each end as Refused. A listing cursor and any text that is not two digit parts keep the equality check only. Nothing is stored and nothing is handed to history. The pull trigger reaches it after each drain.

**Pull run (internal):** `PullRun.run` applies the list-again-once rule: a 400 or a 410 on a stored cursor drops it and lists again without since, once, and a second refusal ends as `Refused`; with no stored cursor a refusal ends as `Refused` at once. `fullList` is true only for a pull that listed from scratch, and a refused first attempt leaves none of its records in the result. It stores nothing and hands nothing to history. The pull trigger reaches it after each drain.

**Pull page decoder (internal):** `PullPageDecoder.decode` turns the text of one pull page into the shared `TranscriptionPage` or refuses it with `PullPageException`; it uses its own small strict JSON reader (`PullPageJson`, nesting deeper than 8 refused). A live record needs `client_id` (a lowercase canonical UUID), `change` (an integer, at least 1), `deleted`, `stored_at`, `key_version` and `encrypted`; a delete record needs the first four and must carry neither `key_version` nor `encrypted`. It does not parse or check the cursor `next` (a non-empty text, returned unchanged), and a refusal message never contains text from the body. `stored_at` must be a non-empty text and its form is not checked there; `PullApplier` parses the date from `stored_at` for a delete record. The pull trigger reaches it after each drain.

**Pull request (internal):** `PullRequest` describes one pull call: the fixed path `/v1/transcriptions` and the optional `since`. `PullRequest.first()` has none; `PullRequest.after(cursor)` keeps the stored cursor text exactly (no trim, no case change, no check of its form) and `query()` writes it percent-encoded (UTF-8 bytes; only A-Z a-z 0-9 - . _ ~ are left alone, a space is `%20`); an empty cursor is refused with `IllegalArgumentException`. `PullStatus.of(status)` reads 200 as `OK`, 400 as `BAD_CURSOR` and every other status as `OTHER`. The pull trigger reaches them after each drain.

**Pulled row body (internal):** `PulledRowBody.read(record)` returns the shared `SyncBody` of one live pulled record at key_version 0 (the codec's `decodePlain` on its `encrypted` text, unchanged). It refuses a delete record, a missing key_version, a key_version other than 0 (the message holds the number; nothing is decrypted) and a missing `encrypted` text with `PulledRowException`; a body the codec refuses becomes a `PulledRowException` whose message is the fixed words plus the codec's family-only message, with the codec's exception as the cause. No message holds text from the record or its body. The pull trigger reaches it after each drain.

**Pull cursor (internal):** the storage keeps one opaque text, the cursor of the last complete pull, in its own table next to the queue: `pullCursor()` reads it, `savePullCursor(cursor)` stores it and a second save replaces it, and `clearPullCursor()` removes it. All three are on `SyncQueueDatabase`; the storage never judges or parses the text, and the pull trigger reaches it after each drain.

**Queue reads (internal):** `isQueued(clientId)` and `queuedIds()` are reads on `SyncQueueDatabase`: whether a client id is waiting in the queue and the ids of every queue row, parked rows included, oldest first. The pull merge uses them (a queued id keeps the local edit; the prune keeps the queued ids); the pull trigger reaches them after each drain.

**Pull applier (internal):** `PullApplier.apply(result)` turns the result of one pull into calls on the core `PullSink`: for a delete record, `deleted_at` is parsed from `stored_at` with `SyncBodyCodec.parseCreatedAt` (exactly three fraction digits); a stored_at the codec refuses counts `unreadable` and calls nothing; an accepted delete goes to `applyRemoteDelete`. A live row whose id waits in the queue (`QueueProbe`) is skipped; any other live row is read and handed to `applyRemoteRow` (a row the store refuses, because a tombstone is held for its id or because it is older than the phone's window, is counted as `refusedByTombstone`); after a finished full list `retainOnly` keeps the list ids and the queued ids. It reads nothing from the network, stores nothing, writes no cursor and starts no pull; the pull trigger reaches it after each drain.

**Pull cycle (internal):** `PullCycle.run` runs one pull in order: the stored cursor is read, `PullRun.run` pulls, `PullApplier.apply` applies, and only then the cursor is saved; after a finished full list one more pull runs from the list's cursor; a second refusal of the stored cursor and of the list clears the stored cursor; at most two pull runs; the pull trigger runs it after each drain.

## Invariants
- Offline dictation, queued by `enqueue`, then pushed by `pushPending` on reconnect, then counted in that call's `SyncReport`; nothing is dropped.
- `enqueue` returns once the row is committed. A second enqueue of the same transcription id keeps the first copy.
- With no `RecordKeys` port every push is built by `SyncBodyCodec.plainPush` at `key_version` 0, and no other key version is built or sent; with a port every push is sealed through the port at its current key version, and nothing is ever pushed in plain form.
- A row is removed only after the uploader answers `CONFIRMED`.
- A drain walks only the rows queued when it started. The highest seq is read once, after the probe answers. A row queued during the drain, including one queued by the uploader, waits for the next drain, so one drain always ends.
- A row the drain cannot push is skipped: its stored source is not `local` or `server`, its client id is not a lowercase canonical UUID, or the codec refuses its body. A skipped row stays queued, the drain goes on to the next row, and each drain that reaches the row counts it in `SyncReport.failed`. A skipped row is never removed.
- A `PermanentRefusalException` with status 400 or 413 parks the row: it stays in the store, marked with its reason (at most 200 characters, never row text), is never retried and never removed, the drain goes on to the next row, and `SyncReport.parked` counts it in that drain (the total is `parkedCount()`). `head`, `nextAfter` and `pendingCount` leave parked rows out. Saving a parked id again unparks and replaces the row in one transaction and keeps its seq; saving a live id again keeps the first copy.
- `FAILED`, and an uploader that throws any other exception (or a `PermanentRefusalException` with another status), stop the drain at that row and count one failure. A `PermanentRefusalException` with status 429 does the same and its Retry-After seconds (`retryAfterSeconds`, 1..3600, else null) ride on the returned `SyncReport`; no other status carries a number, and nothing here waits on it. `UNREACHABLE` stops the drain and counts no failure. A server that is not reachable gives `SyncReport(0, 0)` and no walk over the rows.
- One drain runs at a time (`Mutex.tryLock`). A call made meanwhile returns `SyncReport(0, 0)` at once.
- The migration never drops, hides or deletes a record: a record it cannot convert stays on the server and is counted. It never moves the stored pull cursor, never sees a key, a nonce, an AAD or a plaintext body, and its counts hold numbers only. A complete walk whose only problems are unconvertible records and permanent refusals (400, 413) clears `pending` until the key version changes (a process restart repeats it once); only a transient problem keeps `pending` true: a stop on `FAILED`, an exception or another status starts the walk again at its end, and `UNREACHABLE`, 429 and 409 end the pass and the next drain goes on.
- The pending conversion never drops, hides or deletes a pending row: a row it cannot convert stays on the server and is counted. It never sees a key, a nonce, an AAD, the box key or a plaintext, and its counts hold numbers only. Only a structural fault refuses the whole list (one failure, nothing converted); a row that fails its own checks is skipped, left untouched on the server and counted once (remembered by a fingerprint of its text, never by its id, in memory, at most 10000 entries per set, cleared on a key version change), and a row refused for good (400, 413) or null from the port is not tried again until the key version changes or the process restarts. The skip report (`pendingSkips()`) holds positions only, never row content, and nothing is deleted or changed on the server.
- Decision (pending-sealed list): the list is refused whole only for structural faults (not parseable, over the 8 MiB body cap, not the contract's array, nested too deep); a row that fails its own checks or is permanently refused is skipped, left untouched on the server, counted once and shown to the caller as a count and positions, never content, and is not retried until the key version changes or the process restarts.
- A retry sends the same client id at the same key version, so the server dedupes the pair (N12, ADR-006).
- No sync traffic except to Local Server (N2).
- Sync is off in release builds until Phase 19 (encryption by default): no release build turns it on and no real user's data is synced before then (`docs/04-build-order.md`, "Gates and releases").

## Test Requirement
Every test added or touched for this module must be proven to fail loudly:
break the protected behavior on purpose, confirm the test fails and says why,
then restore the code. A test that only ever passes proves nothing. This
applies to every tier and invariant listed above, not only the ones that seem
fragile.

## How This Module Is Built
One engineer owns this module and delivers it as one pull request, working on
one module at a time. The owner does not write the module's code. The owner:
- splits the work into sub-modules and has sub-agents write each one, code and
  tests;
- coordinates and orchestrates those sub-agents, checks every piece of their
  work, and sends back anything that is wrong until it is right;
- convenes a small council of sub-agents to advise on design, risks and tests
  before and during the build;
- hands the finished, checked module directly to the reviewer as a single pull
  request.
The owner's own work is orchestration, checking and correction, not writing
code.

This is how the project's own team builds modules. It is recommended for AI
agents, not required: an outside contributor may write the code themselves
(`.github/CONTRIBUTING.md`).

## Known Gotchas
- The queue file holds the text in clear on the device. The manifest sets `android:allowBackup="false"` and the backup rules exclude every domain, so a backup does not restore the queue (ADR-028).
- At `key_version` 0 the body is not encrypted, so the server can read the text. This is the development form. It is replaced when the `key_version` 1 form is built.
- A row the drain skips repeats in `SyncReport.failed` on every drain that reaches it.
- A 409 is not covered by ADR-038: it is `FAILED` and stops the drain at its row. It cannot occur today (no client calls the keys route, so no account is above key_version 0); ADR-039 holds the options for the day it can.
- A parked row is not retried and does not go away by itself. A delete removes it (`remove` is not filtered); a retry action is a later feature.
- The client id must be a lowercase canonical UUID. The app's id source (`UuidIdSource`) mints one. A transcription with any other id is skipped on every drain.
- The Android SQLite adapter, `SqliteSyncQueueDatabase`, cannot run on a JVM. Its tests read its source text and check it against `SyncQueueSql`.
- The module imports no auth or crypto module. Modules talk through core ports or the app's wiring (ADR-001). The app supplies the uploader, which carries the user token.
- Known limits of the pull (sync is off in release builds, so none of these runs there; each is to be fixed before sync is turned on):
  - The pull runs inside the drain lock, after the drain loop (`QueuedSyncService.pushPending`). A push that arrives during a pull
    returns at once with nothing sent, so a long full list (up to `PullLoop.MAX_PAGES` pages) skips pushes until it ends. One hung
    read ends the pull as unreachable after the 30 s read timeout.
  - The app's `SyncingHistoryStore.save` commits the save and then enqueues it: two steps. A pull that applies a row with the same id
    between them finds no queued row (`isQueued` is false) and replaces the fresh save.
  - `PullLoop.run` keeps the records of every page in memory and nothing is applied until the last page has arrived. A refusal or an
    unreachable server on page N drops pages 1 to N-1, and the next pull starts again.

## Not Built Yet
- Tombstones for deleted records (a separate sync path, not in the body).
- Everything at `key_version` 1 or higher: the real port adapter in the app, the app's pending transport and the wiring flip (ADR-018, Phases 19 and 20). The own-record migration and re-key pass and the sync half of the pending-sealed conversion are built (see Public Interface).
- ADR-035, wired: the pull. PullRun (PullRun.kt), PullApplier (PullApplier.kt), PullCycle (PullCycle.kt), the pull cursor store and isQueued/queuedIds (SyncQueueDatabase.kt) are in this module, and history implements the PullSink port (core/port/PullSink.kt). `QueuedSyncService` builds a `PullTrigger` over them when the app gives it both a `PullTransport` and a `PullSink`, and `pushPending` runs one pull cycle after a finished drain, under the same drain mutex; the app's `wiring/PullChainWiring.kt` builds the pull transport. A failing pull never crashes the worker and never saves a cursor; the next drain retries. The pull as decided: after each drain of the push queue the module asks the server for the rows changed since its last complete pull. It keeps the cursor `next` of that pull and sends it back as `since`, and it never builds or parses a cursor itself. The cursor is one opaque string in the module's own SQLite file next to the push queue. It moves forward only when a whole pull ended (`more` is false), so an interrupted pull starts again from the stored cursor; it is cleared with the queue on sign-out or account change. The first pull sends no `since`. It repeats the call with `since` set to `next` while the answer says `more` is true, and hands the pulled rows to history. A row is matched by its client id, so a row this device pushed is not stored twice. A pulled live row with the same client id: a local tombstone of any reason keeps the row from being stored and the tombstone stays; an id waiting unsent in the push queue keeps the local edit and the pulled row is skipped; otherwise the row is stored, one row per id. After a full list (a call with no `since`) the module removes the local rows that are not in the answer and are not waiting in its own push queue, so a phone that was revoked and signed in again does not keep rows the server dropped. A 410 answer means the cursor is too old, and a 400 answer means the stored cursor is damaged or of another account: the module drops the stored cursor and lists again without `since`, once per pull; a second refusal stops the pull and counts one failure, no loop. On the server, the push route `POST /v1/sync` and the pull route `GET /v1/transcriptions` are built, and so are the change numbers on the rows (migration 5). The pull route takes `since`, answers a page object with `items`, `next` and `more` (at most 100 records and 4 MiB a page), and answers 410 when `since` is older than the account's purged point. A call with no `since` returns the first page of the live rows.
- ADR-035, wired: deletes. PullApplier (PullApplier.kt) hands every pulled delete record to history's applyRemoteDelete, before its isQueued check (PullApplier.kt:46 comes before :49), so a delete is applied even when the id waits unsent in the push queue; only live rows are skipped through isQueued (SyncQueueDatabase.kt); the pull trigger reaches it after each drain, so a delete made on another device arrives while sync is on. A delete made on another device arrives as a delete record in the same feed as the rows, and reaches history's `applyRemoteDelete`. A remote delete is applied even if this device saved the same id again. A local delete is sent by the `DELETE /v1/transcriptions/{client_id}` route. A queued delete is never refused for good, because an unknown id also answers 204. A local save of an id this phone itself deleted carries the boolean `resave` on that first push only, and never on a retry, so the server knows it is a fresh save and not a stale retry. A pulled delete record always goes to the remote delete call, even if this device saved the id again; the remote tombstone is held across a local re-save. This is not the local rule: a local delete then a local save clears the local tombstone.
