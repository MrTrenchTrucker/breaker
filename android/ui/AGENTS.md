# AGENTS.md — android/ui/

## Purpose
Screens: history, settings, auth, training, and the first-run flow that
takes the user through the permissions Breaker needs (overlay, microphone,
notifications, accessibility) and holds the switch that turns Breaker on and
off. Built so far: the home screen, the settings screen, the first-run flow, the history screen, the How it works screen, the About screen and the auth screen (view and model, no wiring).

**Build phase:** Phase 1 (the app shell's first screens). Each screen arrives with its feature's phase, and the Trucking theme with Phase 22. Needs first: `core` and `shared/ui-tokens` (both on `main`).

## Owns
the home screen (its on/off card, the big mic slot the app's mic view fills, the last transcript with its Copy button, and the menu drawer that offers History, Settings, How it works and About); the home screen's state and the handler of its taps (`screen/home/`), and its host view (`render/HomeHostView.kt`); the How it works and About screens (`screen/howitworks/` and `screen/about/`); the shared transcript card (`screen/history/TranscriptCard.kt`, drawn by Home without a Delete); the auth screen (its state, its texts, its intent handler and its entry `AuthEntry.kt`; its host view `render/AuthHostView.kt`); the MenuIcon and Switch nodes; the brand art views (`render/BrandArtViews.kt`); the gutter (the 16 dp `gutterDp` metric the host applies around every screen's content); the screen node model (`screen/Screen.kt`: Box with pad, gap, spread, outline, edge and onClick; Label with caps and italic; Action with its kit look; TrimStripe; TagPill; CollapsibleText; SegmentedRow; SwitchRow; ValueField; MenuIcon and Switch with their descriptions; BackArrow with its description; Rule; BottomStripes with the plain variant; Spacer; Dot; TouchGap; the KitLook values RAISED, NEUTRAL, DANGER, OUTLINED and TEXT); the title bar (`screen/TitleBar.kt`) and the spacing reader (`render/SpaceScale.kt`); screen components; the first-run flow for a phone with no speech model (screen/firstrun/: the welcome, the five permission pages, the missing list on the last permission page, and the model download page; drawn by render/FirstRunHostView.kt, render/FirstRunPageViews.kt and render/FirstRunDownloadPage.kt); the thin adapters in render/ that read the phone's permission state and open its settings pages; the history screen (the list, copy, delete with a 5-second Undo, load more) and its thin adapters in render/ for the clipboard and the delayed work; every store and clipboard call runs on one process-wide serial dispatcher (screen/history/HistoryDispatcher.kt), and while a read is out the screen shows the last drawn state; consumes `shared/ui-tokens` (Trucking theme); the controls kit, all of it internal - the main, neutral, outlined, destructive and full-width buttons, the switch, the three badges, the text field, the four slanted step marks and the model download bar, over their plain-Kotlin geometry, palette and shade factors and the download bar's numbers (DownloadBarMath) (`ui/controls/` and `ui/render/controls/`); the switch toggles on a tap and reports the new value through onToggled, and a screen reader is told it is a switch with its checked state; the step marks light the current step; a button is as wide as its label plus 16 dp each side, and never narrower than the art's 170 px (113.33 dp), or than the compact floor of 93.33 dp for the History entry buttons that set the compact flag (see the compact width invariant); the text field draws in the monospace face.

## Public Interface
Twelve declarations; everything else in the module is internal or private.
- `createHomeView(context, switch, modelReady, lastDictationAt, lastTranscript, transcriptTime, onCopy, onHistory, onHowItWorks, onAbout, onSettings, onTap, settings, micView, usableHeightDp, onShownMode)`: builds the home screen as a view. It reads the stored theme through `settings` when the view is built. The app passes the switch, the answers for the model, the last dictation and the last transcript, the phone's time for the transcript, the copy request, the four screen requests (history, how it works, about and settings), the request for a take from the big mic, the settings store, the mic view placed in the big slot, the usable height in dp, and the handler handed the mode the view draws in; every fact is read again on each drawing.
- `createSettingsView(context, settings, modelReady, downloadLine, onDownloadModel)`: builds the settings screen as a view. The app passes the settings store, and the model download's answers: `modelReady` says whether the speech model is on the phone, `downloadLine` gives the sentence under the model download (or null), and `onDownloadModel` asks the app to start the download. The model download line is drawn with the ui kit's DownloadBarView. It draws live through the theme controller, not the stored-theme reader.
- `createFirstRunView(context, accessibilityServiceComponent, modelReady, downloadLine, modelDownloadMb, onDownloadModel, settings, onFinished)`: builds the first-run view: the welcome, the five permission pages (microphone, overlay, notifications, accessibility and the keyboard tile) and the model download page, in that order. `onFinished` is called once, when the speech model is on the phone on the download page. The phone's light or dark mode is read once from `context`, and the stored theme is read through `settings` when the view is built; what is granted is read again each time a page is drawn. `onDownloadModel` asks the app to start the download, `downloadLine` and `modelDownloadMb` describe it, `modelReady` says whether the model is on the phone, and `settings` is the app's settings store, in which the microphone prompt flag is kept. The view answers `ModelStepControl`.
- `createHistoryView(context, history, settings)`: builds the history screen as a view. It reads the stored theme through `settings` when the view is built. `history` is core's `HistoryStore` port; `list(limit)` and `delete(id)` are the only calls the screen makes. The screen follows the stored theme and keeps no setting of its own.
- `createHowItWorksView(context, settings)`: builds the How it works screen as a view. It reads the stored theme through `settings` when the view is built. The screen reuses the welcome headings and whys from the first-run pages.
- `createAboutView(context, settings)`: builds the About screen as a view. It reads the stored theme through `settings` when the view is built. The screen shows exactly two lines: what Breaker does and the license. No version line unless one already exists on main.
- `BreakerSwitch`: the interface the app implements: `isOn()`, `switchOn()` (answers `BreakerSwitch.Result`: `On`, `AlreadyOn` or `Refused` with a sentence) and `switchOff()`. The result type is nested in the interface, so it adds no name of its own.
- `DownloadControl`: the interface a view answers to the app for the model download: `refresh()` re-reads the model providers and draws the screen again, `focusDownload()` puts focus on the model step's download button (true when the button was there and was focused, false when the model is ready or nothing is drawn yet), and three download calls with empty defaults: `downloadProgress(doneMb, totalMb)`, `downloadChecking()` and `downloadStopped()`, so a view that draws no bar still compiles. Both calls come from the main thread. The app casts the settings view and the first-run view to it.
- `ModelStepControl`: extends `DownloadControl`; the interface the first-run view answers for its switch notice. Adds `showSwitchRefused(sentence)`: draws a switch-on that the app refused as the notice, the same notice the switch button draws (a blank sentence gives the switch-failed notice). The notice stays through every drawing that follows no tap, until the user acts or a later drawing finds the switch on. The app casts the first-run view to it.
- `HomeControl`: the interface the home view answers (its nested `companion object` also holds `TAP_TO_TALK`, `CANCEL` and `DONE`, read from `HomeTexts`: the one source of the Home mic's three labels, which the app passes on): `showLine(line)` draws the line below the last-transcript box, or nothing for null, `showRecording(recording)` draws the recording look on the big mic, and `refresh()` re-reads the app's facts and draws the screen again. The app casts the view from `createHomeView` to it; all three calls run on the main thread and draw the screen again.
- `createAuthView(context, settings, onSubmit)`: builds the auth screen as a view. The app passes the shared store and the submit callback `(username, password: CharArray, register: Boolean) -> Unit`; the screen carries no text input in this phase, so the submit control refuses until a typing slice lands. What is built here is held by the returned view.
- `AuthControl`: the auth view answers to the app: `refresh()` re-reads the screen's current state and draws it again, and `submitted(register)` returns to idle on the same face after the app's submit attempt finished.

## Invariants
screens render with ui-tokens; light/dark toggle persists (F25).
- This module stores nothing itself. Settings go through the store the app passes in; for the first-run flow, what is granted and whether Breaker is on are read afresh every time the screen is drawn. The first-run flow keeps whether the microphone prompt was asked in the settings store the app passes in (AppSettings.microphoneAsked), written after the prompt came back and read by the setup handler; the notification prompt flag, and the in-memory copy of the microphone flag, live only in the running view. Tested by: `PersistenceGateTest`, `SetupIntentHandlerTest`, `SetupAdapterGateTest`, plus the microphone-step tests in SetupMicStepActionTest and SetupMicStepFlagTest.
- Only the microphone gates the switch. Overlay or accessibility missing shows a warning near the switch; notifications are optional and the switch works without them. The handler does not refuse "switch on" itself: the check is the disabled button on the first-run screen and the app's own `Refused`. The switch on the home screen has no disabled state, and its card does not show the app's `Refused` answer, so the home screen does not check it. Tested by: `SetupModelTest`, `SetupScreenTest`, `SetupIntentHandlerTest`.
- The accessibility service is identified by a name the caller passes in as a String. The name is compared against the phone's list as a whole entry, case-sensitive, in either spelling of a class that starts with the package, and never as a part of a longer name. This module names no class of another module. Tested by: `AccessibilityListTest`, `SetupAdapterGateTest`.
- android.* is named only in render/, in the four entry files (SettingsEntry.kt, FirstRunEntry.kt, HomeEntry.kt and AuthEntry.kt) and in the two info hosts (screen/howitworks/HowItWorksHostView.kt and screen/about/AboutHostView.kt). The auth host is in render/ (`render/AuthHostView.kt`) and the auth entry is in the ui root (`AuthEntry.kt`). Tested by: `AndroidConfinementGateTest`. The history screen (screen/history) imports no android package; its clipboard and its scheduling are seams that the render/ adapters implement.
- The public surface is exactly the twelve declarations above. Tested by: `PublicSurfaceGateTest` and `EntrySurfaceTest`.
- Every button on the first-run view reports one of eight agreed action strings; an unknown string, or any other kind of intent, is not accepted and changes nothing; no branch over the intents falls back to a default. Tested by: `SetupScreenTest`, `SetupIntentHandlerTest`, `NodeModelTest`, `SettingsIntentHandlerSetupTest`.
- Every button on the history screen reports one of six agreed action names (COPY, DELETE, UNDO, MORE, SHOW_ALL, HIDE) inside a History intent. The setup and settings handlers refuse a History intent and a Home intent they do not own; no test checks that yet. Tested by: `HistoryIntentHandlerTest` (an unknown id, action or row, and any other intent, is refused without a call).
- All words the user reads on the first-run view live in one object, are plain ASCII and carry no process words. Tested by: `SetupTextsTest`.
- Home screen: HOW IT WORKS and ABOUT are sent to the app as their own intents (`HomeActions.HOW_IT_WORKS` and `HomeActions.ABOUT`); the app opens the screen, and the drawer closes. The constant `HomeTexts.MENU_NOT_BUILT` is kept, but no screen code draws it any more. Tested by: `HomeScreenTest` (the drawer rows and their intents) and `MenuItemsMapToIntentsTest` (each drawer row maps to its intent).
- All words the user reads on the home screen are `HomeTexts` constants, except the phone's own time for the transcript, the transcriptions themselves, and the take line the app gives through `HomeControl.showLine`, whose words are the app's. Tested by: `HomeTextsTest` (`every text constant is plain ASCII, not blank and free of forbidden words`).
- All words the user reads on the history screen live in one object, `HistoryTexts` in screen/history/: plain ASCII, no process words, and no other user-facing sentence. The timestamp has no word of its own: it is the phone's own short date and time, in the phone's zone. Tested by: `HistoryScreenTest` (every chrome word is a `HistoryTexts` constant). The plain ASCII and no-process-word rule is not checked by any test yet. The failed-read sentence, "Could not load history.", is `HistoryTexts.NOTICE_LIST_FAILED` and sits in the same object.
- A transcription's text never appears in a notice or in an exception message. Every store and clipboard call is guarded, so no exception from them reaches the caller. Copy goes through the clipboard seam and marks the clip as sensitive. Tested by: `HistoryIntentHandlerTest` (a copy that throws shows only the copy failure sentence, with no text and no failure detail) and `HistoryRenderCheckTest` (the clipboard adapter sets the sensitive mark, checked by reading its source text).
- On the history screen, the rows shown so far live only in the running view and are gone when the view is. A delete still waiting for its Undo window is carried out once, right after the view goes, on the serial dispatcher (see the two cases below); if the app dies in that short gap, the rows stay. Tested by: `AsyncHistoryTest` for the close and the deletes, named in the close bullet below; the rows going with the view is not tested.
- The history list opens with 50 rows, newest first, exactly in the order the port returns them. Load more asks the port for 50 more. The cap is 300 rows; when the store holds 300 or more rows, at 300 there is no Load more button and a limit note shows instead, and when the store holds fewer rows than the cap the last page shows neither the note nor the button. Tested by: `HistoryIntentHandlerTest` (the first page of fifty, Load more, the 300 cap, "a store of 280 rows ends at 280 rows with neither the limit note nor Load more") and `HistoryScreenTest` (rows in the port's order, Load more only after a full page, the limit note at the cap, "a short last page at the cap shows neither the limit note nor Load more").
- A long dictation is folded to a fixed number of lines. The plain decision collapse(drawnLines, opened) in screen/history/HistoryCollapse.kt, with its one cap constant COLLAPSE_LINES (6), decides the visible lines and the middle button. The renderer only measures the lines drawn at the card width, with a StaticLayout that copies the TextView's break settings, and applies that answer with an end ellipsis. The opened ids live in the history state and change only through SHOW_ALL and HIDE. Copy always copies the whole stored text. Tested by: `HistoryCollapseTest` (the decision), `HistoryCardNodesTest` (the row's tree, its toggle and the opened ids) and `CollapseRenderRulesTest` (the renderer's source rules). Not proved off a device: the measured line count, and that the break settings match the TextView.
- Delete hides the row at once and, in its place, shows a block reading "Deleted." with an "Undo" action. Nothing is deleted at the tap. Undo cancels the wait and shows the row again; the store is not touched. Tested by: `HistoryIntentHandlerTest` (a Delete opens one window and calls no store; Undo cancels it; a second Undo or a late Undo calls nothing) and `HistoryScreenTest` (the Undo block takes the row's place).
- The Undo window is 5000 ms (UNDO_WINDOW_MS). When it ends, the row is deleted once through the port. A false or thrown result shows "Could not delete it." and the list is drawn again from the port. When a window ends on its own, the screen is drawn again through the view's change hook. Tested by: `HistoryIntentHandlerTest` (the window is 5000 ms; the window end deletes once and hands the screen to the change hook once; a refusal and a throw both show the delete failure, and the row comes back). These tests fire the window by hand with a fake scheduler; real time is not checked. `HistoryRenderCheckTest` checks the hook by reading the host's source text.
- A first read that fails shows "Could not load history." (`HistoryTexts.NOTICE_LIST_FAILED`) in place of the list and never the empty-state line. A Load more read that fails keeps the rows shown and shows the sentence once; the next read that works clears it. Tested by: `HistoryScreenTest` (a failed first read) and `HistoryIntentHandlerTest` (a Load more read that throws; a good read after a failed one).
- Two cases, stated separately. If the app dies inside the Undo window, nothing is deleted: the rows stay in the store, so this case fails safe. If the screen closes, or rotates so that the view detaches, every pending delete is carried out once, right after, on the serial dispatcher, each exactly once: this case fails towards delete, on purpose. If the app dies in the short gap between the detach and those deletes, the rows stay in the store, the same fail-safe as a death inside the window. Tested by: `HistoryIntentHandlerTest` (close deletes each pending row once and leaves no live window), `AsyncHistoryTest` (`closing with two pending deletes draws nothing and deletes both once in tap order`, `a second close after a reattach commits the new pending deletes`) and `HistoryRenderCheckTest` (the host closes the model once on detach, before the superclass is told, checked by reading its source text). The first case, app death inside the window, is not tested by any test. A delete the store refuses while the screen is closing or rotating is silent: the row stays in the store, and the user has already seen "Deleted."
- The only scheduling is behind the DelayedWork seam. Its real implementation is in render/ViewDelayedWork.kt, the only file that uses postDelayed and removeCallbacks. `HistoryRenderCheckTest` checks that by reading the source text: only that file uses the two calls, its cancel removes the posted runnable, and SettingsEntry.kt holds none of the scheduling words. Across the main tree, the scheduling words and GlobalScope, withContext, async and Dispatchers.Main appear in code only in that file, except that the async file may use launch. No test runs the real queue.
- Rotation ordering holds only when the old view's close is submitted before the new view's first read. An Activity recreate tears the old view down first, so it is covered. Building the new view before the old one is detached is not covered: a deleted row can show once until the next read. Tested by: `AsyncHistoryTest` (`a deleted row can show once when the new view reads before the old view closes`), which pins this limit and does not claim it is safe.
- A result posted from the serial queue to a detached view is parked by View.post until the view is attached again. Every result carries the epoch of the view's life it was made in, and reattaching moves the epoch on, so a parked read, tap or window-end result from before the close is dropped when it runs after the reattach; a read is also dropped if a newer read or tap was made after it. A delayed window runnable that fires after close finds its pending entry gone and draws nothing. Tested by: `AsyncHistoryTest` (`a tap result parked across a close and a reattach is not drawn`, `a window end result parked across a close and a reattach is not drawn`, `a window end result after the view closed is not drawn`, `a window runnable that fires after close finds nothing pending and draws nothing`, `a notice from a read parked across a reattach is not shown on the next tap`).
- A read whose result is dropped carries its failed-read notice forward: the notice is shown as a second notice after the next result's own notice, so the sentence is not lost; a read drawn later clears it. Tested by: `HistoryNoticeCarryTest` and `AsyncHistoryTest` (`a dropped read does not swallow the list failure sentence`, `a good read drawn after a dropped failing read leaves no carried sentence`, `the carried sentence is not doubled when the tap shows it too`).
- The model's scope has no exception handler. A store exception that escapes the handler's own guards ends the app, as the old main-thread call did. Tested by: none in the tree yet.
- Rows past the 90-day retention may still show until the app calls the history module's purge (ADR-010: a row expires when it is more than 90 days old at the purge). This screen does not call the purge. Tested by: none in the tree yet.
- The first-run view is drawn again when the window gets focus back, so a permission granted on a system page shows on return. Pinned by a text scan only. Tested by: `SetupAdapterGateTest`.
- The theme choice on the settings screen is three cells, System, Light and Dark. Each cell sends SetThemeMode with the stored mode's enum name ("SYSTEM", "LIGHT" or "DARK"), and the selected cell is the stored mode, so System is selected while the app follows the phone. An unknown name is refused and writes nothing; the setup handler refuses it too. Tested by: `SettingsAppearanceTest` (the three cells and their names) and `SetupIntentHandlerThemeModeTest` (the setup handler refuses each mode name).
- The auth screen keeps no typed password: the typed characters live in a CharArray the app can zero, the zero-fill runs in a finally so it happens whether the submit callback returns or throws, and the screen refuses a submit it has no text for (the submit control hands an empty array until a typing slice lands). No state, no label and no toString carries password text. Tested by: `AuthIntentHandlerTest` (the zero-fill and the throw path) and `AuthStateTest` (the pinned labels).
- The first-run download bar's percent is the whole part of done over total, at most 99, so 100 is never shown before the check starts, and it is absent when the total is not known (the bar is then whole and striped). Tested by: `DownloadBarMathTest`.
- Every screen entry (a top level `create...View` function) builds its theme with the shared reader `storedTheme(settings, ...)` in theme/StoredTheme.kt, except createSettingsView, which draws live through the theme controller. `StoredThemeSourceRuleTest` scans all entry files and pins that each one except the settings view has the line `val theme = storedTheme(`; the arguments of that line are pinned only for the first-run, home and history entries (`FirstRunThemeGateTest`, `HomeThemeGateTest`, `HistoryRenderCheckTest`). Tested by: `StoredThemeSourceRuleTest`.

- The host root is the one padding place. The app's `applyInsets` pads each screen's root by the system bars, the display cutout and the 16 dp gutter, and no screen adds its own outer padding. A Box pads only its own children, through its `pad`. Rule and BottomStripes are top-level nodes of a screen, drawn full width through the host's padding by `RuleView` and `BottomStripesView` (`render/BleedViews.kt`); the Home, Settings and History hosts each call `ScrollView.openForBleed()`. Tested in part by `LauncherScrollGateTest` (the app's root padding); the bleed views have no unit test.
- Spacing: every distance a screen draws is a `Space` name (NONE, XS, S, M, L, XL) given to a Box's `pad` or `gap`, or to a `Spacer`. A `Dot` is drawn as a square one step S wide. `render/SpaceScale.kt` reads each name from the ui-tokens metrics by its own name (`spaceXsDp` to `spaceXlDp`), and the renderer turns it into pixels by the screen's density. Sizes that are not spacing (the art, bar heights, stroke widths) stay in `HomeGeometry`. Tested by: `NoPrivateSpacingGateTest` (a bare number in render/ is refused, and the scale names are listed), `SpaceScaleTest` and `SpacingRenderRulesTest`.
- Compact buttons: a button is as wide as its label plus 16 dp each side, and never narrower than its floor. The default floor is the art's 170 px, 113.33 dp (`BUTTON_MIN_WIDTH_DP`), and is unchanged. The compact floor is 93.33 dp (`BUTTON_COMPACT_MIN_WIDTH_DP`, 140 / 1.5 dp), read off the History mock-up `breaker_history_long.png`, where COPY, SHOW ALL and DELETE are drawn at 140 px each. Why: the 16 dp gutter and the 16 dp card padding on each side leave 296 dp inside a card on a 360 dp phone; three default buttons need 340 dp and do not fit, while three compact buttons with two 8 dp gaps need 280 + 16 = 296 dp and fit exactly. Only the History entry rows set the compact flag (`Action.compact` and the `transcriptCard` compact parameter); Home COPY and every other button keep the default. A long label still grows its button past the floor, and the touch height stays at least 48 dp. The compact width adds no colour and no ui-tokens entry. Tested by: `ControlsCompactWidthTest` (the floors, the growth and the 360 dp fit) and `CompactButtonRulesTest` (the flag passes through the views and the geometry).
- No screen code (`screen/`) names a stock Android widget. The stock views are named only in the render layer (`render/`) and in the HostView files. The two stock containers allowed by name are `android.widget.LinearLayout` (the column a rendered screen is put in, in the settings activity) and `android.widget.ScrollView` (the page scroller a host wraps a screen in, in that activity). A `FrameLayout` is used only in a HostView file (the Home host's overlay and the first-run host's root). `NoStockWidgetGateTest` pins the rule.
- Title bar: Settings and History begin with the title bar of `screen/TitleBar.kt`: a back arrow, the title in italic capitals, and a full-width accent rule under them. Home has no title bar: its top row is the menu icon and the logo word, under a thin accent rule drawn across the top of the screen.
- The Home host (`render/HomeHostView.kt`) is a FrameLayout over the page scroller. The drawer overlay (the dim, at `HomeGeometry.DRAWER_DIM`, and the panel) is added over the page only while the menu is open. While the menu is open, a tap that is not a drawer item only closes the menu, and a tap on the dim closes it. Back closes it as well (see Known Gotchas). Tested by: `HomeScreenTest` (the drawer rows and their intents) and `MenuItemsMapToIntentsTest`. `HomeHostView` also writes two diagnostic log lines under the tag `BreakerMicProbe` (in `show` and `attachMicSlot`), only while the big mic records; they belong to the debug mic probe and are removed with it before release.
- Home mic slot (F45, ADR-026): the mic is the overlay module's ScreenMic, built by the app and passed in as `micView`; `HomeHostView.attachMicSlot` puts it in the slot tagged `HomeNodeIds.MIC`, `HomeGeometry.slotHeightDp(usable)` tall (the usable height less the non-mic parts, held to `MIC_SLOT_MIN_DP` 100 and `MIC_SLOT_MAX_DP` 150), full width with `CENTER_HORIZONTAL`, so the mic is centred. The Home mic's three labels have one source: `HomeControl.TAP_TO_TALK`, `CANCEL` and `DONE`, read from `HomeTexts`; the app passes them to the overlay. Tested by: `HomeFitTest` (the clamp), `HomeHostViewTest`, `HomeHostMicCentringGateTest`.
- A redraw re-parents the mic: `show()` runs on every redraw (`showLine`, `showRecording` and `refresh` each draw the screen again) and builds a new tree, so `attachMicSlot` removes the mic from its old parent before it adds it (without that the first resume threw IllegalStateException). Tested by: `HomeHostMicParentGateTest` (source text). Whether a redraw during `RECORDING` cancels a touch on the mic is OPEN (one lead for the stuck X and check, see Known Gotchas).
- Rule R2, the render layer: every custom or plain View measures itself (`onMeasure` from its own size, `resolveSize`), never the default; a View built outside a draw and re-added on a redraw is detached from its old parent first; a value that may be unset on some path (lateinit, lazy) is never passed eagerly; no redraw re-parents a view in the middle of a touch gesture on it. `TouchGapView` (`render/NodeViews.kt`) measures `resolveSize(side, spec)` on both axes: with the default measure it took the whole AT_MOST height in the ScrollView's fill pass (`openForBleed`), the top bar became window-tall and Home was blank on a 1440x3120 phone. Tested by: `TouchGapMeasureGateTest`, `TouchGapRulesTest`. OPEN: the rest of the render layer is not yet audited against R2 (see the History defect in Known Gotchas). Layout and lifecycle changes are proven on an Android 16 emulator before an APK ships; JVM tests and source-text gates cannot see layout.
- Rule R3, one gutter in one place: bars and cutout are margins on the screen root, the 16 dp gutter is padding, applied once, and every screen uses the same content edge. OPEN: Settings is drawn in a narrower band than Home (see Known Gotchas).
- The Settings view draws live through the theme controller. `SettingsHostView` redraws the whole screen when the theme changes, and its model download bar takes the same theme, so no part keeps a fixed theme. The view has no setup block and no History button; its sections are the theme, the routing, the three switches, the server and API key values, and the speech model row.

- Planned (ADR-033), not built: Home carries a quiet notice with a way to sign in, drawn from a state the app passes in. This module opens no sign-in screen by itself and nothing here blocks dictation, history or settings when the user is signed out.

## Test Requirement
Every test added or touched for this module must be proven to fail loudly:
break the protected behavior on purpose, confirm the test fails and says why,
then restore the code. A test that only ever passes proves nothing. This
applies to every tier and invariant listed above, not only the ones that seem
fragile.

## How This Module Is Built
One engineer owns this module and delivers it as one pull request, working on
one module at a time. The owner does not write the module's code. The owner:
- splits the work into sub-modules and has sub-agents write each one, code and
  tests;
- coordinates and orchestrates those sub-agents, checks every piece of their
  work, and sends back anything that is wrong until it is right;
- convenes a small council of sub-agents to advise on design, risks and tests
  before and during the build;
- hands the finished, checked module directly to the reviewer as a single pull
  request.
The owner's own work is orchestration, checking and correction, not writing
code.

## Known Gotchas
- FIXED, History list (defect from the phone test of APK 8; fix in main, emulator-proven by the gate reviewer, not yet seen on the project owner's phone): with 1 to 3 rows, shorter than the window, the first card was stretched to the window height and the other cards were 0 px, on every draw. Cause: two plain Views with no `onMeasure` in `render/ScreenRenderer.kt`, the spread-row separator (`separatorOf`) and the horizontal spacer (`spacerOf`, re-sized by `placedChild`), took the whole AT_MOST height in the ScrollView's fill pass; the same class as `TouchGapView` (rule R2). Both are now the platform `android.widget.Space`, written fully qualified because the bare name `Space` in that file is the `ui.screen.Space` enum; `SpaceMeasureGateTest` reads the source and refuses a plain `View` in either path. Emulator (API 36), 1 row: 1965 px to 660 px at 1080x2400 and 2544 px to 880 px at 1440x3120; 3 rows: three cards of equal height where the old build showed one. Required, and still the rule: every transcription is a card in a scrolling list, newest first, Load more after 50, each folded to `COLLAPSE_LINES` (6); only a card whose text is longer than the fold gets its own Show all / Hide, which opens that card only.
- OPEN, Settings gutter: Settings uses a narrower band than Home on the project owner's phone; NOT reproduced on the emulator (its edges match Home), so a phone screenshot is needed; one hypothesis is that the gutter is applied twice (the app's Settings column and ScrollView both get insets and the host adds its own gutter; an extra 4.8 dp was measured once). Required (rule R3): Home, Settings, History, How it works, About and First run share one gutter in one place and one content edge.
- OPEN, Home mic: while recording the X and the check are drawn but do not answer a tap (cause not found); the Home mic does not yet show the tile's MIC_BUSY and SENDING faces; it follows the phone's light/dark setting, not the stored theme. The mic is the overlay module's; its card holds the detail.
- Back closes an open Home menu. On Android 13 and newer the Home view registers a Back callback only while the menu is open, and that callback closes the menu through the same intent the dim sends. On Android 11 and 12 the activity's older Back path asks the Home view to close the menu first. Not verified on a device.
- The kit's Ready, Phone only and Failed badges (`render/controls/BadgeView.kt`) are drawn by no screen. The Settings model row draws its READY badge as a plain node (`screen/settings/SettingsBlocks.kt`).
- The history screen takes core's HistoryStore port through android_core; the module never imports the history module.
- Consumes shared/ui-tokens — do not hardcode colors in screens.
- The restricted-setting state cannot be read by any public API, so that step only explains: it has no status and no "Open app info" button.
- The texts on the first-run view are drafts still to be checked. The accessibility limits are written from the accessibility decision record and are not word for word the service description.
- Breaker stays off after the user switches it off only if the app does not switch it on again at start.
- "Asked before" for the notification prompt lives in the view only. For the microphone it is also kept in the settings store once the prompt has come back, so it survives a restart. After a refusal in an earlier session, or after the view is rebuilt, the first tap on the notifications button may seem to do nothing. If the system answers a microphone request at once and no screen drawing follows, the first microphone tap does nothing visible and the next one opens the app's page. On Android 11 and later a tap outside the microphone dialog dismisses it without an answer; the flag is still set, and the system's rationale check then answers false (it answers true only after a refusal), so the next tap opens the app's page instead of asking again, although the system would still show the dialog. This is harmless: the user can grant the microphone there.
- A notice lasts one drawing and has no live region, so a screen reader is not told when it appears. A focus change right after a tap may clear it at once.
- The history notices and the Undo block carry the same no-live-region limit as the setup notices. No test checks this.
- First run: an interrupted download starts again from zero; there is no resume.
- First run: a view rebuilt during a download shows the start button until the next progress report. A tap there goes to the app, which refuses a second download while one runs (it answers AlreadyRunning), and nothing is shown.
- First run: the welcome and permission pages show again after the app closes before the download finishes, because the done marker is written only when the model is on the phone on the download page.
- First run: the percent is rounded down and never reads 100 before the check starts. With an unknown total there is no percent line; the bar is whole and striped and the megabytes so far show.
- First run: the permission pictures are fixed PNG files in drawable-nodpi; their colours are not theme tokens.
- The named catches in AndroidSetupPlatform (ActivityNotFoundException, SecurityException and RuntimeException) stay on purpose: they name the failures expected, and the adapter check requires the names.
- Auth screen: there is no text input yet, so the submit control refuses until a typing slice lands (the host hands the handler an empty array, which the policy refuses as too short, and no submit callback fires).
